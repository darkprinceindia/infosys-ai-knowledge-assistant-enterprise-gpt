INFOSYS ENTERPRISE GPT - PRESENTATION SPEAKING GUIDE
AI Knowledge Assistant capstone prototype

Suggested length: 10-12 minutes, followed by a 3-5 minute live demo.
This guide matches the 15-slide capstone presentation. Speak naturally rather
than reading every sentence word for word.

IMPORTANT CONTEXT TO STATE AT THE START
This is a capstone prototype with fictional sample documents. The presentation
screens were captured from the locally running application. A public review
demo is now available at https://infosys-enterprise-gpt-demo.onrender.com/ .
It is not an official Infosys system or an approved place for real internal
documents.

ONE-SENTENCE SUMMARY
Enterprise GPT is a permission-aware knowledge assistant: an employee asks a
question, the application finds relevant approved passages, and it gives a
source-linked answer only when it has enough permitted evidence.

3. THE COMPLETE SYSTEM IN ONE PICTURE (SLIDE 4)
==========================================================================

Use this simple flow while pointing to the architecture diagram:

Browser UI
   -> Python HTTP API (app.py)
      -> query classifier and route decision
         -> HR: read-only MCP search tool (mcp_server.py)
         -> other questions: local search (knowledge.py)
            -> SQLite documents and search index (data/app.db)
      -> access and freshness checks
      -> cited answer or explicit no-answer
   -> browser displays the result and source links

Suggested words:
"The browser never reads the database directly. JavaScript sends an HTTP request
to our Python API. The API authenticates the user and decides where to search.
The search reads indexed document passages from SQLite. The API filters those
passages by access and document status, builds an answer, records the event, and
sends JSON back to the browser. The browser renders that JSON as the answer and
source cards."

If someone asks what 'backend' means, say: "It is the server-side Python code
that handles login, search, permission checks, answer construction, and storage.
The frontend is the HTML, CSS, and JavaScript that users see and click."

4. HOW DOCUMENTS ENTER THE SYSTEM (SLIDE 5)
==========================================================================

Suggested words:
"First, an administrator provides an approved TXT, Markdown, DOCX, or PDF file.
The form also asks for a title, department, access classification, source owner,
document type, and effective and expiry dates. The backend checks the file size,
type, readable content, and duplicate content. Then it extracts text, divides it
into sections and overlapping passages, and indexes those passages."

Why each step matters:
- Validation keeps unsupported, oversized, empty, or duplicate files out.
- Section chunks help the assistant cite the relevant part of a document.
- Metadata lets the app filter by department, classification, and freshness.
- The index makes passages searchable when an employee asks a question.
- An audit record shows that indexing happened.

Current demo limit: uploads are at most 5 MB. PDF text extraction uses pypdf;
TXT, Markdown, and DOCX handling otherwise relies mainly on Python's standard
library. The five seeded documents are fictional examples.

5. HOW A QUESTION BECOMES AN ANSWER (SLIDES 6-7)
==========================================================================

Suggested words:
"A signed-in employee asks a question. The backend classifies its department
using simple topic words, unless the user selected a collection. HR questions
demonstrate a read-only MCP connector. Other questions search the local index.
After retrieval, the app checks that the user can access each source and that
the document is active and not expired."

"The search score combines three local signals: term overlap, a hashed lexical
vector comparison, and SQLite FTS5 full-text rank. These are ways to rank text
matches. The local vector is NOT a semantic model embedding, and the displayed
retrieval signal is NOT a probability that the answer is correct."

"When the evidence is strong enough, the app chooses up to three passages. If a
Gemini API key is configured on the server, Gemini can write a concise answer
from those permitted passages. Without that key, the app extracts relevant
source sentences and adds citations. If the passages are too weak, it returns
an explicit no-answer message. The result, route, citations, timing, and audit
event are saved for review."

Access example to explain on slide 7:
"The administrator can get a cited answer from the fictional HR leave policy.
A Delivery employee asking the same HR question receives insufficient evidence
with no HR passage or citation. This shows why authorization belongs inside
retrieval and after connector output, not only in the page design."

What MCP means here:
MCP is a structured tool interface. This prototype starts a local Python
server over standard input/output using JSON-RPC. Its read-only
'search_curated_knowledge' tool handles the HR demonstration. This is not a
live connection to a company HR system. The Python API checks the tool's
returned passages again before using them.

6. TECHNOLOGY: WHICH PART USES WHAT, AND WHY (SLIDES 8-9)
==========================================================================

Frontend - static/index.html, static/style.css, static/app.js
  Technology: HTML, CSS, and browser JavaScript.
  Work: forms, navigation, role-specific screens, calling API endpoints,
  showing answers, source cards, dialogs, feedback, and analytics.
  Why: a small interface that runs without a frontend build step.

Application backend - app.py
  Technology: Python standard-library ThreadingHTTPServer and JSON endpoints.
  Work: login, signed session cookies, request validation, query routing, MCP
  call orchestration, answer construction, and API responses.
  Why: keeps the capstone easy to run and makes the full data flow visible.

Knowledge and retrieval - knowledge.py
  Technology: Python plus SQLite and FTS5 full-text search.
  Work: document extraction, chunking, indexing, permission checks, ranking,
  source preview, feedback storage, and analytics calculations.
  Why: one local store supports the demonstration without a separate search
  service. For a much larger production corpus, this design needs replacement.

Connector - mcp_server.py
  Technology: MCP-style JSON-RPC over local standard input/output.
  Work: a read-only HR knowledge search tool.
  Why: demonstrates a controlled tool boundary and visible routing.

Optional answer model - Gemini API, called only by the backend
  Work: turns retrieved permitted passages into a short cited response.
  Why: improves wording when configured. Extractive synthesis keeps the core
  workflow functional without an API key. The browser does not receive the key.

Storage - data/app.db
  Technology: SQLite tables and an FTS5 index.
  Stores: users, document metadata and text, chunks, search features, queries,
  citations, feedback, connector calls, and audit events.

Examples of frontend/backend links:
- Login form -> POST /api/login -> session cookie.
- Ask form -> POST /api/query -> answer plus citation JSON.
- Citation click -> GET /api/documents/{id} -> permitted source preview.
- Upload form -> POST /api/documents/upload -> validation and indexing.
- Analytics page -> GET /api/analytics -> administrator metrics.

The code excerpt on slide 9 shows the HR routing decision and the extra
permission check after the MCP tool returns a result.

10. QUICK ANSWERS TO LIKELY QUESTIONS
==========================================================================

Q: Did you train a new model on company documents?
A: No. This is retrieval-based question answering. It searches approved
   passages and uses them as evidence. Gemini is optional for wording.

Q: Is the search a semantic vector database?
A: No. The current prototype combines term overlap, local hashed lexical
   vectors, and SQLite FTS5. Production-scale semantic retrieval would require
   evaluated model embeddings and an appropriate store.

Q: What happens if there is no reliable source?
A: The assistant returns a no-answer message and no source citation.

Q: Can one department see another department's restricted documents?
A: On a fresh request, the backend filters retrieval and source previews by
   role and department. A known UI issue can retain an old displayed answer
   after account switching, so that client state must be cleared before the
   product can claim a complete role-switch boundary.

Q: Why use MCP?
A: It gives a structured, read-only tool boundary for a curated knowledge
   search. HR questions demonstrate that route; other questions use the local
   index. The API still validates returned passages.

Q: Does the system need Gemini to work?
A: No. Without the API key it makes a source-grounded extractive answer.

Q: Are the shown metrics performance or accuracy benchmarks?
A: No. They summarize local demo activity. Citation coverage and a retrieval
   score do not prove that an answer is correct.

Q: Is it deployed and ready for real Infosys documents?
A: A public review demo runs at
   https://infosys-enterprise-gpt-demo.onrender.com/ . It contains fictional
   sample content. Real company content needs the production controls and
   approvals described above.

FOR UNDERSTANDING: HOW THE WHOLE PROGRAM FITS TOGETHER
==========================================================================

These are study notes to help you explain the project in your own words. The
short speaking script above is for the slides; this section goes through the
working parts in the order they are used. Think of the program as a library
desk: a person asks a question, the desk checks who they are, finds pages
they are allowed to read, and gives an answer that points to those pages.

THE WHOLE JOURNEY IN ONE LINE

Person in browser -> static/app.js -> app.py -> knowledge.py or mcp_server.py
-> SQLite knowledge bank -> app.py -> static/app.js -> answer on the page.

The arrows are ordinary requests and responses. The browser sends data to
the Python server over HTTPS; the server sends JSON data back. The browser
never opens the database or uses the Gemini API key directly.

1. WHAT IS READY BEFORE ANYONE ASKS A QUESTION?

When app.py starts, it calls knowledge.py to create the database tables and
seed the demo accounts and sample documents. The database is data/app.db, a
SQLite file. data/source_metadata.csv tells the program which five Markdown
files to import and supplies their department, access classification, owner,
type, and dates. The document text and searchable passages are stored in the
database. The samples are fictional teaching examples, not Infosys policies.

The five starting documents are:
- Delivery escalation SOP: P1/P2 severity, who to notify, client updates,
  and incident closure. It is marked Internal.
- Employee leave policy: annual leave, sick leave, and policy precedence.
  It is marked HR.
- API incident runbook: triage, safe rollback, and escalation. It is marked
  Engineering.
- Approved AI services positioning: client claims and proposal review. It
  is marked Sales.
- Project onboarding manual: project setup and first-week review. It is
  marked Internal.

"Department" helps organize and route a search. "Classification" decides
who may read a document. In this demo, employees can read Internal content;
HR, Sales, and Engineering content is limited to the matching department;
Restricted content is for the administrator. The administrator can read all
classifications. A Delivery employee can read the Internal delivery SOP, but
not the HR leave policy. The backend applies these rules, not just the page.

2. HOW THE FRONTEND AND BACKEND TALK

static/index.html defines the visible pages and forms. static/style.css makes
them look like the Infosys-inspired demo. static/app.js is the browser code
that listens for clicks, reads form values, calls the server, and fills in
the page. app.py is the Python HTTP server. It serves those static files and
receives API requests such as /api/login, /api/query, and /api/documents.

For example, clicking "Ask assistant" does not search a document inside the
browser. static/app.js sends a small JSON message to POST /api/query. The
server replies with JSON containing answer text, citations, route, timing,
and a retrieval signal. static/app.js turns that reply into the answer card.
The site is one program because each part passes a clearly defined result to
the next part.

3. HOW LOGIN WORKS

The login dropdown in static/index.html offers the demo administrator and
four employee accounts. The selected account and typed password go through
static/app.js to POST /api/login in app.py. app.py looks up that account in
SQLite and asks knowledge.py to verify the stored password hash. On success,
app.py gives the browser a signed session cookie that lasts up to 12 hours.
The browser sends this cookie with later requests, so the server knows which
demo user is asking. On page reload, GET /api/me checks the session again.

The accounts use the shared demo password set by DEMO_PASSWORD in the server
environment; the login screen does not display it. There is no employee
self-registration in this prototype. The frontend hides administrator-only
buttons for employees, and app.py also refuses administrator operations from
an employee. Hiding a button alone would not be a security check.

4. A QUESTION'S STEP-BY-STEP JOURNEY

Use this example: "How do we escalate a P1 delivery incident?"

1) You type the question or click its suggestion on the Ask assistant page.
   You may leave Collection as All or choose one collection yourself.
2) The ask() function in static/app.js sends the question and collection to
   POST /api/query in app.py. The signed login cookie goes with the request.
3) app.py checks the cookie, finds the user's role and department, and checks
   that the question and collection value are valid.
4) knowledge.py classifies the topic from simple clue words unless you chose
   a collection. Here, "P1", "delivery", and "incident" point to Delivery.
5) app.py chooses the search route. Delivery uses knowledge.py directly.
   HR routes through the MCP tool explained below.
6) knowledge.py searches stored document passages in SQLite. It first keeps
   only active documents that have not expired, fit the collection filter,
   and are accessible to this user. It ranks the remaining passages using
   word overlap, a small locally calculated text vector, and SQLite FTS5
   full-text search. It is not a learned semantic embedding model.
7) app.py checks that the leading passages have enough evidence and keeps at
   most three for the answer. If nothing is strong enough, it says it lacks
   evidence instead of inventing an answer.
8) If Gemini is available, knowledge.py sends the question and ONLY those
   permitted passages to Gemini using a server-side key and asks for numbered
   source citations. It accepts the model's answer only if its citation
   numbers point to the supplied passages. If Gemini is unavailable or its
   answer fails that check, knowledge.py builds a simpler answer by selecting
   relevant sentences from the passages.
9) app.py records the question, route, answer status, response time, source
   links, and an audit event in SQLite. It sends the answer and citation
   details back as JSON.
10) renderAnswer() in static/app.js shows the answer, [1]/[2] source cards,
    route, model/fallback label, retrieval signal, and time. Clicking a source
    card calls GET /api/documents/{id}; app.py and knowledge.py check access
    again before showing the source preview.

In this example, the Delivery escalation SOP can supply the P1 escalation
steps: notify the on-call delivery manager within 15 minutes, open an
incident record, and start a bridge with the engineering lead. The source
card shows where that answer came from. The percentage called "Retrieval
signal" describes a text-match score; it is not the probability of truth.

5. WHAT QUESTIONS CAN I ASK?

Ask about information actually present in the five sample documents, such as:
- "How do we escalate a P1 delivery incident?" -> Delivery escalation SOP.
- "What is the annual leave request process?" -> Employee leave policy.
- "When should an API deployment be rolled back?" -> API incident runbook.
- "What requires review before a client proposal?" -> Sales positioning.
- "What is on the new project checklist?" -> Project onboarding manual.

An HR example follows the same overall path, but step 5 calls the MCP
connector. An HR employee or administrator can receive a leave-policy
citation. A Delivery employee asking the same question should not receive
the HR-only passage. You can also ask about a newly uploaded document after
it has been indexed. A question about a topic absent from all permitted
sources should produce the insufficient-evidence message.

6. WHAT RAG MEANS IN THIS PROJECT

RAG means Retrieval-Augmented Generation. In everyday terms: look up the
right pages first, put those pages beside the question, then write an answer
from them. Here, the "retrieve" part is knowledge.py searching SQLite. The
"augmentation" is app.py passing selected source passages to the answer
step. The "generation" part can be Gemini or the local sentence-selection
fallback. A citation links the answer back to the page used.

There is no LangChain library or separate frontend chaining engine here.
The chain is the order of our own functions: browser submit -> API login
check -> classify -> search -> evidence check -> answer -> save -> display.
MCP is a tool boundary inside that chain for HR questions, not the whole RAG
system. No new model was trained on these documents.

7. HOW AN ADMINISTRATOR ADDS A DOCUMENT

Only an administrator sees "+ Add document" in the Knowledge library. The
form asks for a title, file, department, classification, source owner,
document type, and optional effective and expiry dates. Supported files are
TXT, Markdown, DOCX, and text-readable PDF, up to 5 MB. A scanned PDF with
no extractable text will not become useful knowledge without OCR, which this
prototype does not provide.

Suppose the administrator adds a fictional "Equipment request guide" with
General department and Internal classification. Its text could say:
"Employees request a laptop through the service desk. Their manager approves
the request before IT assigns a device." After indexing, a user can ask,
"How do I request a laptop?" and the new guide can become a cited source.

The upload path is:
1) static/app.js reads the selected file in the browser, converts its bytes
   to base64 text, adds the form metadata, and sends JSON to
   POST /api/documents/upload.
2) app.py checks the login and administrator role, decodes the file, and asks
   knowledge.py to extract its readable text.
3) knowledge.py checks the file type, 5 MB limit, required metadata, allowed
   department/classification, enough readable text, and whether identical
   text is already indexed. The duplicate check uses a SHA-256 checksum.
4) knowledge.py divides the text by headings and into short overlapping
   passages. For each passage it stores searchable words, a local lexical
   vector, and an FTS5 search entry. It also stores the full extracted text,
   metadata, active status, and an audit entry in data/app.db. It does not
   keep the original uploaded file bytes as a separate download.
5) app.py returns the new document ID and passage count. static/app.js shows
   an "Indexed ... passages" message and refreshes the library.

The form says "approved document", but the software does not independently
approve or scan a file. The administrator must choose appropriate content.
On Render Free, uploaded records are temporary because data/app.db is on an
ephemeral filesystem; a restart or redeploy can remove them. The five
fictional starter documents can be seeded again.

8. WHAT THE CONNECTORS PAGE AND MCP ACTUALLY DO

The Connectors page shows the one configured connector, "curated-knowledge",
and a small routing picture. static/app.js asks GET /api/connectors;
app.py returns its name, MCP stdio JSON-RPC protocol, tool name, scope, and
a "ready" label. That label is configuration information, not a live test
of a remote company service. This page does not let a user add connectors.

For an HR question, app.py starts mcp_server.py as a separate local Python
process. It sends structured JSON-RPC messages through the process's
standard input: initialize, then call search_curated_knowledge with the
question, logged-in user ID, and department. mcp_server.py looks up the user
and calls knowledge.py's permission-filtered search on the SAME SQLite bank.
It returns matching passages through standard output. app.py checks access
again before using them. If the MCP call errors, app.py falls back to local
search and records that route. This is a real local MCP-style tool call, not
a connection to a live HR website or an external policy database.

Why include it? MCP demonstrates how a future approved tool could be called
through a clear boundary while the main backend stays responsible for access
checks. Successful and failed MCP calls are saved as connector events for
administrator review. Non-HR questions normally use the local index
directly, so they do not create an MCP event.

9. WHAT QUALITY ANALYTICS SHOWS

Quality analytics is visible only to an administrator. Opening it, or
clicking Refresh, makes static/app.js call GET /api/analytics. app.py checks
the administrator role, then knowledge.py reads saved database activity and
calculates the figures. The browser draws the cards, bars, and recent rows.
It is a view of stored events, not a second AI model or a live data stream.

What is on the current page:
- Total questions: how many questions have been recorded.
- No-answer rate: the percentage that lacked enough source evidence.
- Citation coverage: the percentage not marked "no answer". This is a
  simple activity measure, not a test that every answer is correct.
- Average response: average backend query time in milliseconds.
- Documents by collection: number of active documents per department.
- Retrieval routes: how many questions used local search, MCP, or fallback.
- Recent questions: the latest question, collection, route, and whether it
  received an answer.
- Connector events: recent MCP call status, number of returned sources, and
  connector time.

For example, asking the P1 delivery question adds one to Total questions,
adds a Local hybrid index route, and places the question in Recent questions.
Asking the leave question can add an MCP route and a connector event. If a
question has no permitted evidence, No-answer rate can increase. Clicking
"Yes" or "Needs work" under an answer sends a rating to POST /api/feedback;
app.py checks that it belongs to the user (or admin) and stores it. The
backend also calculates feedback count and average rating, but this version
of the Quality analytics page does not display those two values.

These numbers help an administrator spot missing documents or a failing
connector. They are not measured accuracy, business impact, or proof that
the assistant gave correct policy advice. On Render Free, the activity
history can reset with the temporary database.

10. IMPORTANT FILES AND THEIR JOBS

static/index.html          Page structure: login, ask form, library, connector
                           view, analytics view, and source dialog.
static/style.css           Colors, layout, typography, and responsive styling.
static/app.js              Browser actions, JSON API calls, and screen updates.
app.py                     HTTP server, endpoints, sessions, access checks,
                           route decision, MCP call, answer and event logging.
knowledge.py               SQLite setup, starter documents, text extraction,
                           passage indexing, search, permissions, Gemini/local
                           answer functions, and analytics calculations.
mcp_server.py              Read-only local MCP search tool for HR route.
prompts/grounded_answer.txt Instructions sent with permitted passages when
                           Gemini is used.
data/source_metadata.csv   List and metadata for the five starter documents.
data/sample_*/             The five fictional Markdown source documents.
data/app.db                SQLite runtime knowledge bank and activity log;
                           created by the app and not committed to Git.
.env / Render variables    Password, signing secret, optional Gemini key,
                           host, port, and model; not browser code.
render.yaml                Template for a Render Blueprint deployment.

The files are linked by function calls and HTTP endpoints, not by putting
everything in one giant file. static/app.js never imports knowledge.py;
it talks to app.py over the network. app.py imports knowledge.py, and for
HR questions starts mcp_server.py, which also uses knowledge.py. Both read
the same SQLite data so uploaded documents can be searched later.

"First, our administrator loads fictional approved guides into a searchable
knowledge bank. The browser sends a signed-in user's question to the Python
